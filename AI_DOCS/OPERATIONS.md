# Рабочий процесс ИИ-агента

## 1. Перед изменением

1. Уточнить конкретную страницу, концепт и версию.
2. Проверить ветку и текущее состояние файлов в GitHub.
3. Прочитать HTML, связанный CSS/JS и относящиеся к задаче ресурсы.
4. Проверить, не описано ли уже требуемое поведение в `PROJECT_CONTEXT.md`, `PLAN.md` или этой документации.
5. Определить минимальный набор файлов для изменения.

Не предполагать, что код из предыдущего обсуждения всё ещё актуален: повторно прочитать файлы перед записью и использовать свежие SHA.

## 2. Реализация

- Сохранять существующую архитектуру статического сайта.
- Не смешивать редизайн одной версии с исправлениями других страниц.
- Не добавлять тяжёлые зависимости для простой клиентской интерактивности.
- Для медиа сохранять доступные элементы управления, осмысленный `aria-label`, клавиатурный фокус и корректное поведение на мобильных устройствах.
- При замене постера на iframe проверить, что iframe получает корректные `title`, `allow`, `allowfullscreen` и referrer policy.
- Не выдавать текущий постер Kinescope за последний кадр видео без проверки.
- Не включать в Git локальные отчёты, виртуальные окружения, кеши и оригиналы скриншотов, которые исключены через `.gitignore`.

### Контент и аудитория

Style of Mind — сайт психолога, работающего методом системных расстановок. Тексты и интерфейс должны помогать посетителю разобраться в подходе, услугах и способах связи со специалистом, не оказывая давления.

- Не придумывать сведения о специалисте, квалификации, отзывах, ценах, услугах или результатах работы.
- Не добавлять гарантии психологического или терапевтического результата и не использовать манипулятивные формулировки.
- Сохранять ясность условий работы и пути к записи.
- При существенном изменении смысла текста сверять его с контекстом страницы; не считать редактирование копирайта чисто визуальной правкой.

## 3. Проверки

Минимальная проверка перед публикацией:

1. Проверить изменения на предмет пробелов и конфликтных маркеров: `git diff --check`.
2. Запустить статический аудит ссылок и локальных ресурсов.
3. Проверить синтаксис изменённых JavaScript-файлов через `node --check`.
4. Запустить браузерный аудит и проверить горизонтальное переполнение на ширинах 1440×900, 768×1024, 390×844 и 320×740.
5. Проверить соответствующие интерактивные сценарии: меню, якоря, кнопки, FAQ/галереи/попапы, а также запуск видео — по затронутой функциональности.
6. Посмотреть скриншоты после изменения визуального оформления.
7. Проверить публичную GitHub Pages страницу после публикации и статус GitHub Actions, если применимо.

Локальные команды Windows описаны в `../LOCAL_PREVIEW.md` и `../AUDIT_TOOLING.md`. Для быстрой проверки страницы можно использовать `check_site.bat` или команду `tools/site_tools.py` из инструкции предпросмотра.

Если среда проверки недоступна, перечислить, что было проверено фактически, а что осталось непроверенным. Не заявлять об успешном визуальном тесте на основании одного лишь чтения кода.

## 4. Коммиты и публикация

- Работать в `main`, если пользователь не указал другую ветку и это допускают права репозитория.
- Использовать актуальный SHA каждого файла при обновлении через GitHub API.
- Не выполнять параллельные обновления одного и того же файла.
- Разбивать независимые файлы на отдельные коммиты, если инструмент не поддерживает атомарный многофайловый коммит; затем проверить, что все изменения присутствуют.
- Не применять force push/reset для синхронизации истории.
- Не коммитить непроверенные изменения как полностью готовые без явного указания ограничений.
- После записи повторно получить файлы из GitHub и подтвердить наличие ожидаемых изменений.
- Коммит в GitHub не равен подтверждённой публикации: дождаться обновления Pages/Actions или прямо обозначить, что публичный результат ещё не проверен.

## 5. Документация и итоговый отчёт

Если изменение меняет структуру, поведение, внешний ресурс, команду проверки или известное ограничение:
- обновить соответствующую документацию;
- не копировать один и тот же подробный список версий в несколько мест без причины;
- сообщить какие файлы изменены, какие проверки выполнены, какие коммиты созданы и что не удалось проверить.

## 6. Приоритеты

При конфликте руководствоваться в таком порядке:
1. Прямые требования пользователя в текущей задаче.
2. Фактический код и поведение целевой страницы.
3. `PROJECT_CONTEXT.md` и `PLAN.md`.
4. Эта инструкция и остальные справочные документы.

Если задача допускает несколько решений, выбрать самое простое, которое соответствует запросу и сохраняет существующее поведение.

## 7. GitHub Actions и автоматические коммиты

Перед изменением файлов в `.github/workflows/` читать workflow целиком и проверять триггеры, permissions и список файлов, которые он может записывать.

- `site-browser-audit.yml` запускает QA для v4.1 при изменениях путей, перечисленных в `on.push.paths`, либо вручную; это не полный аудит всех концептов.
- `optimize-portrait-assets.yml` срабатывает при изменении скрипта оптимизации или самого workflow. Он имеет `contents: write` и автоматически коммитит/пушит сгенерированные ассеты в `main`. Не запускать и не менять этот workflow, не понимая последствий; избегать циклических триггеров и неожиданных изменений опубликованных ресурсов.

После изменения workflow проверить YAML, ограничения запуска, permissions, список изменяемых файлов и фактический результат Actions. Не считать наличие workflow доказательством успешного последнего запуска.
